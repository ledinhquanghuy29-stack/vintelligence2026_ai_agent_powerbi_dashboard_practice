# Build Log

A round-by-round record of how this dashboard was actually built: what broke, why, and what was learned. The semantic model (TMDL) and report pages (PBIR JSON) were generated by Python scripts rather than hand-built in Power BI Desktop, so most of the bugs here are "wrote the JSON/DAX slightly wrong" rather than "clicked the wrong thing" — the kind of issue a text-based, scriptable Power BI workflow surfaces that a point-and-click build wouldn't.

For the finished design, see [`DASHBOARD_INSTRUCTION.md`](DASHBOARD_INSTRUCTION.md). For findings and business context, see the [README](../README.md).

---

## Phase 1 — initial model and report

Built the semantic model (tables, Power Query, Date table, relationships, calculated columns, DAX measures) for sales, delivery, inventory, and returns, then validated it by opening the project in Power BI Desktop and checking it against four independent reconciliation totals (see `DASHBOARD_INSTRUCTION.md` §6) — all passed on the first real open. Report pages (originally 6, later restructured) were then generated as PBIR JSON directly.

## Round 1 — first screenshots, several small fixes

First look at the rendered report surfaced a batch of issues at once:
- Slicers (Year/Month) defaulted to a tall scrolling list, with no indication of the data's actual date range.
- Currency wasn't shown on any monetary card.
- Pages had a lot of unused vertical space.
- Text was small throughout.
- The "Seasonality Index by Calendar Month" chart showed all 12 months at exactly 1.00 — flat, when the underlying data has real seasonality (0.52–1.62 across months).

Fixes: added a VND/USD suffix to every currency measure's `formatString`; bumped font sizes; tightened page layout; and (wrongly, as it turned out — see Round 2) attempted to fix the Seasonality Index measure, which used `ALLSELECTED('Date'[Month Number])` to remove the current month's filter while the chart's axis actually grouped by a *different* column, `'Date'[Month]`. `ALLSELECTED` only lifts filters on the exact column named, so the denominator was accidentally computed inside the same single-month filter as the numerator.

## Round 2 — the fix that didn't take, and why

The user reported the Seasonality Index chart was "still the same" after the Round 1 fix. The real cause: the TMDL file had been edited *while Power BI Desktop still had the project open*. Desktop keeps its own in-memory copy of the model and, when the user later closed it, Desktop wrote that stale in-memory copy back to disk — silently reverting the edit.

**Lesson, applied for the rest of the build:** before editing any `.tmdl` or report JSON file, confirm Power BI Desktop is fully closed (`Get-Process PBIDesktop,msmdsrv` returns nothing). With Desktop actually closed, the measure was re-fixed, this time using `CALCULATE(..., ALL('Date'))` — removing every filter on the whole `Date` table unconditionally, rather than relying on `ALLSELECTED` to target the exact right column.

## Round 3 — tables don't stretch to fill their container

A detail-row table given the full page width still rendered with a visible block of bare page background beside it, and 3 of 5 rows were clipped, needing an inner scroll to read.

Root cause, found from the screenshot rather than guessed: **Power BI's modern table visual does not stretch its columns or background to fill a wider container than its content needs** — it draws itself only as wide as the content requires (header-or-value width, whichever is larger, per column) and leaves the rest as blank page background, not a padded card. Separately, the real row height was ~55px, not the ~28px assumed.

Fix: every detail table is sized to an estimate of its real content width (by column count/type) and height (`~70px + ~55px × data rows`), **never stretched**. The space freed beside a table holds a chart on the same dimension instead of blank canvas — and that chart, unlike the table, renders correctly at any height, so it stretches all the way to the bottom of the page.

## Round 4 — Phase 2 (Customers, Reviews, Web Traffic) and two model bugs

Added `Customers`, `Reviews`, `WebTraffic` tables and a global colour/style pass (custom slicer "Dropdown" style, line chart "Linear" interpolation — both best-effort, undocumented PBIR properties, since no official schema confirms per-visual style overrides). Two real model errors surfaced on open:

1. **Ambiguous relationship path.** Desktop refused to load with: *"There are ambiguous paths between 'OrderItems' and 'Reviews': 'OrderItems'->'Orders'->'Reviews' and 'OrderItems'->'Products'->'Reviews'."* `Reviews` had two active relationships to the same two parent tables (`Orders`, `Products`) that `OrderItems` also relates to — a diamond the engine won't resolve automatically. Fixed by setting `Orders → Reviews` to `isActive: false`, keeping `Products → Reviews` as the only active path.
2. **Backwards relationship direction.** After fixing #1, the next load failed with: *"Column '' in Table '' contains a duplicate value '58970' ... not allowed for columns on the one side of a many-to-one relationship."* Three new relationships had `fromColumn`/`toColumn` reversed — e.g. `Customers.customer_id → Orders.customer_id` instead of `Orders.customer_id → Customers.customer_id`. The rule, confirmed against every working Phase-1 relationship: **`fromColumn` is always the many/child side (the column that can repeat); `toColumn` is always the one/parent side (must be unique).**

## Round 5 — whitespace fix for real, Promotions, a KPI swap, merged pages

A `Stockout Rate %` / `Overstock Rate %` swap on Executive Overview made room for two Phase 2 KPIs without adding a second card row. The two separate Customer pages were merged into one. `promotions.csv` was added to the model.

The real fix for leftover whitespace (Round 3 had addressed table width, but a screenshot still showed a gap below a table): **decouple the chart's height from the table's height.** A table stays sized to its content (more height just adds blank space inside the table itself); the chart beside it stretches all the way to `PAGE_H − DETAIL_Y − 20` regardless of what height the table needs. This is the pattern used everywhere from this point on.

## Round 6 — a report-wide colour theme and more chart variety

Added a custom theme (`StaticResources/RegisteredResources/SupplyChainTheme.json`, registered via `report.json`'s `themeCollection.customTheme` + a second `resourcePackages` entry) — the first change in the build to touch `report.json` itself rather than one visual, so it was deliberately kept to the handful of top-level keys Microsoft's own basic-theme documentation uses, to minimize the chance of an unrecognized key rejecting the whole theme (and with it, the whole report). Also swapped three single-series column charts for donut charts, and merged two line charts into one `lineClusteredColumnComboChart`.

## Round 7 — a critical self-review, as a Supply Chain Manager

Asked to review the dashboard critically rather than just fix bugs. Found:
- A "Net Revenue by Promo Channel" chart's **largest bar was an unlabeled `(Blank)` group** (orders with no matched promotion) — technically correct, practically confusing.
- The new combo chart's secondary-axis line was too thin to read against the columns.
- Some charts showing a flat/non-ranking pattern had a caveat in the title; others showing the *same* kind of pattern didn't — inconsistent.

Fixes: a new calculated column, `OrderItems[promo_channel_label] = IF(ISBLANK(RELATED(Promotions[promo_channel])), "No Promotion", RELATED(Promotions[promo_channel]))`, replaced the blank group with an explicit label (reusing the same `RELATED` pattern already used elsewhere in the model — no new risk). The combo line's `strokeWidth` was increased. Caveats were added consistently to every chart title showing a flat or volume-not-value pattern.

## Round 8 — a real SKU-level exception table, built from the official schema

A product-level "which SKUs are overstocked right now" table had been deferred twice as too risky (it needs a visual-level filter, a JSON pattern not attempted elsewhere in this build). This round, the official Microsoft PBIR schema files were fetched directly (`filterConfiguration/1.3.0`, `semanticQuery/1.4.0`) instead of guessed from community examples — and it worked on the first real attempt (one self-caught bug: a doubled `"field"` wrapper in the sort definition, fixed before testing).

Added `Inventory[is_latest_overstock]` (flags the latest-snapshot rows over the agreed 180-day threshold) and a filtered, sorted table on the Inventory page. Two caveats worth remembering: the "latest snapshot" date is **hardcoded** (would need updating if the source data is ever refreshed past Dec 2022), and the 180-day threshold is **fixed** — a calculated column can't react to the page's own "Overstock Days Threshold" slicer, since columns are computed once at refresh time, not per filter context.

## Round 9 — moving a section without growing the canvas

Asked to move the "Site Traffic" reference panel back onto the Customers page, but explicitly *not* by giving that page its own taller canvas again (an exception made once already, in Round 4, and deliberately removed in Round 5 so every page shares one size). Fix: Site Traffic now occupies the exact bounds of one driver-row chart slot — replacing "Net Revenue by Age Group", which was dropped because it showed the same flat "tracks customer count, not value" pattern already shown by "Net Revenue by Acquisition Channel" next to it. No information lost, zero change to the page's height. All six pages share the same 1,920×1,300 canvas with no exceptions.

## Round 10 — recolouring the report and rebuilding the Data Quality page

Two asks: make the report-wide colour palette nicer, and clean up the Data Quality page, which was still a plain reconciliation table plus three stacked paragraphs of text with no visual hierarchy.

**Colour palette.** Because no chart in this build sets its own `dataPoint` colour overrides, every chart inherits its series colours from `SupplyChainTheme.json` in series order — so the whole report could be recoloured by editing one file. The old 8-colour set mixed fully-saturated hues (pure red, pure orange, pure green) that fought each other for attention. Replaced with a set of similar lightness/saturation (a cohesive blue → teal → amber → slate → purple → sage → terracotta → navy progression), plus softened `good`/`bad`/`neutral` semantic colours to match. No chart JSON needed to change for this.

**Data Quality page.** Added two new, additive-only helpers in the generator (`panel()` for colour-coded text cards with a background/border, and a `RECON_TABLE_STYLE` object for the table) rather than changing the existing `textbox()`/`table()` signatures used by the other five pages, to keep this change isolated:
- The reconciliation table now has a solid-colour header band, white header text, and banded row shading, instead of default plain styling.
- The six exception facts that used to be buried inside one dense paragraph are now six individual number chips (big bold number + short caption), coloured amber as a consistent "caution" accent — scannable at a glance instead of requiring the paragraph to be read end to end.
- The three remaining text blocks became three colour-coded cards side by side (KPI Definitions in blue, Known Limitations in slate — pulled up from the README since it belongs next to the other caveats on this page, Recent Fixes in green), each with its own tinted background and matching border instead of being plain black text with no boundary.

All of this reuses `background`/`border`/`columnHeaders`/`values`/`grid` visual object properties, which are the same category of best-effort-but-long-documented Power BI formatting properties already used for table styling in earlier rounds — not a new kind of risk, just more of it on one page.

## Round 11 — a manager's critique, and a confirmed Desktop limitation

Asked to review the dashboard as an E-commerce Manager rather than just check it renders. Verdict: the pages look clean but the Executive Overview KPI cards are just raw numbers with no way to tell "is this good or bad" — no comparison to a prior period, no target, no colour signal. Two real design flaws came out of this review too: several "by Year" charts (Gross Margin % Promo vs Non-promo, Distinct Customers by Year) collapse to a single bar the moment a manager filters to one year, which is the most natural thing to do with a Year slicer; and some KPI cards (Delivered Within SLA %, Return Rate %) have no stated target at all, so a flat percentage can't be judged on its own.

Agreed with the user on a scoped pilot (Executive Overview only, before touching the other 4 pages): 6 new measures in `_Measures.tmdl` (`displayFolder: Comparisons`), each returning a pre-formatted status *string* rather than a number, so no conditional-formatting JSON is needed — the colour comes from a literal 🟢/🔴 emoji character in the string itself:
- **YoY measures** (Net Revenue, Gross Margin %, Distinct Customers, Repeat Customer Rate %): anchor on `MAX('Date'[Year])` in the *current* filter context (not `ALLSELECTED`, deliberately, after the Round 1/2 lesson about `ALLSELECTED` targeting the wrong column) and compare it to that year minus 1, via two `CALCULATE(..., 'Date'[Year] = X)` variables that override whatever Year the slicer has selected. This makes "vs last year" meaningful whether the slicer is at its All/All default (compares 2022 vs 2021) or filtered to a single year (compares that year vs the one before it) — resolves the tension between "keep All/All as the default" and "show a real YoY delta."
- **Target measures** (Delivered Within SLA % vs 95%, Return Rate % vs 5%): agreed-on assumed targets, since the source data has no stated business target for either — flagged to the user as assumptions, not derived facts.

Added `kpi_row_compare()` to the generator: a second, shorter Card visual stacked directly under each value card, bound to the new label measure, sized so the pair's total height matches the original single card's height exactly (85px + 28px ≈ 115px) — no other row on the page needed to move.

**Confirmed, not just suspected: Power BI Desktop does not honour `background`/`border` objects on a `textbox` visual.** The Round 10 Data Quality page had been opened and re-saved by the user in Desktop since it was built; its visual.json files came back with every `background`/`border` object stripped out, while `columnHeaders`/`values`/`grid` on the reconciliation table — and plain text colour — survived untouched. This is a definitive answer where Round 4's "best-effort, unconfirmed" note could previously only guess: text colour and table styling are real, persisted features; a coloured card *background* via `textbox` is not, at least on this Desktop version. The coloured "cards" on the Data Quality page render as colour-coded headers and numbers only, not as tinted boxes — a real gap from the original design intent, left open for a future round (likely fix: a `basicShape` rectangle visual placed behind the text as its own layer, since shape fill is a long-documented, reliably-persisted property, unlike background on a textbox).

## Round 12 — fixing what was actually misleading, and one currency

A second manager-style review sorted remaining issues by severity; this round fixed the ones that made numbers misleading, before any cosmetic work:
- **Two measures on different scales sharing one axis.** "Return Units and Refund Amount by Reason" plotted ~20K units next to ~100M in money on the same axis, so the units columns were effectively invisible. Now a `lineClusteredColumnComboChart` with Refund Amount on its own secondary axis.
- **Days of supply in the tens of thousands.** The overstocked-SKU table showed values like 38,280 days (~105 years) — mathematically right (near-zero sales), practically unbelievable. Added `Inventory['Days of Supply']` (text, capped at "> 365") and `Inventory['Stock Value']` (`stock_on_hand × RELATED(Products[cogs])`), and the table is now ranked by stock value tied up rather than by days — so the SKUs that cost the most sit at the top.
- **A donut label rounding real revenue to "0bn".** Casual's ~349M was labelled "0bn (2.79%)" because the donut's data labels round to whole "bn". Replaced with a bar chart, which also reads better when one category holds ~80% of the total.
- **Lines were smoothed, and had been all along.** The `interpolation` property set back in Round 4 was never a real property and was silently ignored. The actual cause, found by searching the Fluent2 base theme file shipped with the report: the theme sets `lineStyles.lineChartType: "smooth"` for line charts. The correct per-visual override is `lineStyles.lineChartType = 'linear'`, now applied to all 7 line/combo charts. Lesson: when a style property "doesn't take," search the base theme JSON in `StaticResources/SharedResources/BaseThemes/` for the real property name before guessing again.

**Currency is now $ everywhere.** The source data never states a currency; the earlier VND/USD split was an inference from scale (prices ~1,000x larger than shipping fees). Switched every money `formatString` to `$#,0`/`$#,0.00` so the report uses one label throughout. The scale gap still exists in the data (shipping fee ≈ $5 against an average order value in the tens of thousands) — the currency label changed, the numbers did not.

## Round 13 — readability pass and an Overview rebuild

The rest of the review, done as one batch because every item used a pattern already proven in this build:
- **No more raw column names.** Projections now carry a `displayName` (e.g. `product_name` → "Product"). Values that were snake_case in the data got calculated label columns built with `SUBSTITUTE` + capitalise-first-letter: `Returns['Return Reason']`, `Customers['Acquisition Channel']`, `Orders['Order Status']`, and `OrderItems[promo_channel_label]` itself.
- **The grey line under every chart title** was the Fluent2 base theme's `subTitle` (on by default), repeating raw field names. Hidden per visual alongside the title.
- **Titles name, they don't interpret** — every "flat throughout…", "tracks customer count…" clause removed. Targets stay where they're a reference (SLA ≥ 95%, return rate ≤ 5%), which also fixed a stale "target: 100%" left over from before the targets were agreed.
- **Monthly charts no longer scroll.** The `Year-Month` text axis was categorical, so 126 months needed a scrollbar showing ~3 years at a time. Added `'Date'[Month Start]` (a real date) so the axis is continuous and all 10 years fit. This also fixed the "by Year" charts collapsing to one bar under a single-year filter — every Year-axis chart became a Month Start line.
- **No donuts.** Every remaining donut became a bar/column chart. Receipt-to-Sales Ratio (flat at 1.15–1.18 for 11 years) was replaced by Ending Stock Value by Category, using a new `Ending Stock Value` measure (latest snapshot only, never summed across months — same pattern as `Ending Stock`).
- **Units**: `Avg Lead Time` and `Avg Days to Return` now format as "x.x days".

**Executive Overview rebuilt without tables.** The Category Summary table was dropped (the same breakdown lives on Sales and Inventory as detail tables) in favour of four charts that each fill their row to the bottom of the page — no table-height gaps. The compare-card row from Round 11 rendered wrong: at 85px the value card clipped its caption, and at 28px the label card showed nothing. Now 100px + 50px, with the label card's caption hidden (`categoryLabels.show = false`) and a fixed 12pt font. The Overview gets its own row grid below the taller card row; the other five pages keep the shared one.

**Process slip, caught in time:** the model edits this round were made while Desktop was still open from the previous screenshot check — the one rule this build has followed since Round 2. The regeneration step's own Desktop check stopped the run; Desktop was then closed *without saving*, and every edit was re-verified on disk before regenerating. The check belongs before the first edit, not just before the generator.

## Round 14 — a bug that had been there since Phase 1

Cross-checking the dashboard against numbers recomputed straight from the CSVs (pandas, outside Power BI) turned up a real model bug: **`OrderItems[has_promo]` was TRUE for every row.** It was defined as `NOT ISBLANK(promo_id) || NOT ISBLANK(promo_id_2)`, but `Csv.Document` loads an empty CSV cell into a text column as an empty string `""`, not a blank — and in DAX `ISBLANK("")` is FALSE. So "Gross Margin % (Promo)" silently equalled overall margin and "Gross Margin % (Non-promo)" was always blank. Visible symptoms, all of which had been on screen for several rounds without being traced back: the Promo vs Non-promo chart only ever drew one series, and the reconciliation table's `Diff Weighted List Margin vs Non-promo Margin` column was empty. Fixed with `LEN(...) > 0`, which is false for both `""` and blank. The README's promo finding (−14% vs +20%) was computed in Python during EDA, so it was right all along — it just wasn't what the model showed.

Also: the six Overview compare labels are now in English, and each names the years it compares ("▲ 12.3% (2022 vs 2021)"). Without that, a card reading 9.7% (all-time margin) above "▲ 3.4 pts vs 2021" read as if 9.7% were the 2022 figure. The YoY values themselves were verified against the CSVs: +12.3% net revenue and +3.4 pts gross margin, 2022 vs 2021.

## Round 15 — honest comparisons, and the last of the layout gaps

- **Like-for-like YoY.** The four YoY labels now compare only months that have data in *both* years (`FILTER` over `'Date'[Month Number]` where Net Revenue is non-blank in each year), and say so when it's fewer than 12 ("2013 vs 2012, 6 mo"). Without this, 2013 vs 2012 compared a full year to Jul–Dec 2012 and showed inflated growth.
- **Return rate's last month.** Dec 2022 read ~1.1% against ~4–5% for every other month — not an improvement, just orders whose returns hadn't arrived yet. Measured from the CSVs, order-to-return lag runs 5–31 days and returns stop at 2022-12-31, so `Return Rate %` now excludes orders placed after (last return date − 31). This trims the KPI slightly and removes the false dip.
- **Overview category row** split into Gross Margin % by Category and Overstock Rate % by Category, each on its own axis. Return Rate % by category was dropped from this page: ~4% in every category, and unreadable beside Overstock's ~55–63%.
- **Table cards now end where their neighbouring charts end** on all four detail pages (same height, `grid.rowPadding` raised from the theme's 4 to 10 so rows fill more of the card). `fontSize` on table headers/values was added as best-effort — it is not in the base theme.
- **Data Quality page**: the build-log card (developer history) was replaced with "KPI Targets and Comparisons" and "Which Date Each Page Uses", laid out as a 2×2 grid. Writing the second card surfaced a real limitation worth stating openly: `Reviews` relates to `Products` (active) but not to `Orders` (inactive since Round 4's ambiguous-path fix), so the Customers page's Year/Month slicers don't filter review counts or ratings.

## Round 16 — two more end-of-data effects, and Overview slicers

- **Reviews now follow the date slicers.** Every review measure (`Review Count`, `Average Rating`, `Positive/Negative Review %`) filters `Reviews` with `TREATAS(VALUES(Orders[order_id]), Reviews[order_id])`. This passes the current set of orders (after date, region, channel and customer filters) onto reviews without touching relationships — `Orders → Reviews` stays inactive, so the Round 4 ambiguous-path error can't come back. Before this, filtering the Customers page to 2022 still showed 114K reviews (all ten years).
- **Delivered Within SLA % had the same end-of-data bias as return rate, in the other direction.** From the CSVs: lead time is at most 10 days and deliveries stop at 2022-12-31, so for orders placed in the last 10 days only the fast deliveries were recorded — Dec 2022 read 77.4% against ~75% for every other month. The measure now excludes orders placed after (last delivery date − 10).
- **Overview slicers**: Region, Category and Channel added beside Year and Month. Channel is a new `Orders['Order Channel']` label column over `order_source`. The page's purpose line says which charts respond: inventory charts follow date and category only, since `Inventory` has no path to geography or orders.

## Round 17 — choosing chart types for what the data actually does

Started from one chart: monthly Gross Margin % swung from +20% to −40% and back, too spiky to read. Before picking a replacement, checked *why* it swings: margin correlates −0.83 with promo revenue share, and the 27 negative-margin months average ~80% of revenue from promotions against ~22% otherwise — all in Jul–Sep and December. So the fix needed to separate "trend" from "cause":
- **Overview**: Gross Margin % and Median Days of Supply now show **12-month rolling** values (`CALCULATE(..., REMOVEFILTERS('Date'), DATESINPERIOD('Date'[Date], MAX('Date'[Date]), -12, MONTH))`), blank until a full 12 months of data exist so the first points aren't built on a half-window. `REMOVEFILTERS('Date')` lets the window reach back into the prior year when the page is filtered to one year.
- **Sales**: the trend row is now two combos — Net Revenue + Orders, and **Promo Revenue Share (columns) + Gross Margin % (line)**, which shows the cause of the dips directly. The Promo vs Non-promo line chart became **Gross Margin % by Promo Status**, two bars (new `OrderItems['Promo Status']` column).
- **Targets drawn as lines**: `SLA Target` (95%), `Return Rate Target` (5%), `Overstock Rate Target` (30%), each blank wherever its actual is blank so the line doesn't run past the data. SLA and return rate plot them as a second line series; overstock by category uses a combo with `valueAxis.secShow = false` (confirmed in the base theme) so the target line shares the columns' axis rather than getting its own scale.
- **Refund by reason** is a ranked bar instead of a combo whose line implied an order between unordered reasons. All `clusteredBarChart` visuals now sort descending by their measure.
- **Average Rating by Category** (3.92–3.94 everywhere) replaced with **Positive Review % by Month**.

The first open failed: *"TMDL objects cannot be merged because both declare the same property: expression — Measure 'Promo Revenue Share %'"*. The model already had a `Promo Revenue Share %` (built on `[Promo Net Revenue]`, same logic) from an earlier round; this round added a second one under the same name. Removed the new copy, then scanned every table for duplicate measure and column names — none left. Lesson: grep the model for a name before adding a measure.

## Round 18 — the custom theme had never loaded

Every screenshot since Round 6 showed bright blue `#118DFF`, navy `#12239E` and orange `#E66C37` — the first three colours of the **Fluent2 base theme**, not the custom palette. Cause: `report.json` registered the custom theme with `path: "SupplyChainTheme"`, while the file on disk is `SupplyChainTheme.json`. Desktop couldn't resolve it and silently fell back to the base theme, so the Round 6 and Round 10 palette work never rendered. Fixed `name` and `path` to `SupplyChainTheme.json`, matching how Desktop itself registers imported themes.

With the palette actually loading, colours were then given fixed meanings: navy for the main actual, teal for volume, amber for promotions, green/red only for good/bad, grey dashed for targets.
- **Good/bad by value** without conditional-formatting rules: split measures, each with its own colour. `Overstock Rate % (Within Target)` (green, capped at 30%) and `(Above Target)` (red) stack to the full rate in a `lineStackedColumnComboChart` with the grey dashed 30% target on the same axis; `Gross Margin % (Positive)` / `(Negative)` in a stacked column, so each promo-status bar takes the colour of its sign.
- **Per-series colours** (`dataPoint` with `selector.metadata` = the series' queryRef), **per-category colours** for ratings 1–5 (`dataPoint` with a `scopeId` comparison on `Reviews[rating]`), and **dashed target lines** (`lineStyles.lineStyle` with a series selector) — all best-effort, none in the base theme; if Desktop ignores them the chart falls back to theme colours.

## Round 19 — the promotion cycle, comparison cards everywhere, navigation

- **A finding, not an artifact.** The rolling 12-month margin steps between ~12% (even years) and ~7% (odd years). It was first written off here as a synthetic-data pattern; the user pointed out the data is real, and the CSVs explain it: odd years run 6 promotion campaigns at ~21% average discount (extra Jan–Mar and Jul–Sep campaigns), even years 4 at 15%, while non-promoted margin holds near 20%. Added to the README's key findings, and the Sales page now has **Promo Campaigns and Gross Margin % by Year** (new `Promo Campaigns Started` measure: promotions whose `start_date` year is in the current year context — `Promotions` has no date relationship). The "synthetic" wording was removed from the README and the Data Quality page.
- **Scatter instead of a combo**: Gross Margin % vs Promo Revenue Share, one dot per month (`scatterChart`, roles Category / X / Y). The 126-column combo it replaces was too dense to show the −0.83 relationship.
- **Overstock chart decluttered**: series renamed through projection `displayName` (Within target / Above target / Target) and the target line's data labels switched off with a per-series `labels` selector.
- **Comparison cards on every page.** 18 more label measures, generated by script from the same template as the Overview's: YoY (percent, percentage points, or absolute with a unit) with a "good direction" per KPI — e.g. Discount Rate, Lead Time, Shipping Fee, Refund Amount and Ending Stock count a decrease as green; Avg Days to Return is neutral (⚪) — plus vs-target status for Overstock (≤ 30%) and Stockout (≤ 5%). The shared row grid moved down 37px to fit the taller card row; every page still ends at 1,280.
- **Page navigator** (`pageNavigator`, styled by the base theme) in the header of all six pages.
- **Data Quality cards get real backgrounds**: a `shape` rectangle (fill + outline) sits behind each chip and card at a lower z-order, with the text inset on top — the replacement for the textbox background Desktop strips (Round 11).

**Follow-up after the first screenshot:** the Promo Campaigns combo was unreadable — the column colour didn't apply (columns and line both navy), labels overlapped, the numeric Year axis showed only 2015 and 2020, and 2012 (half a year, no campaigns) skewed the line. Replaced with a single **Gross Margin % by Year** column chart: bars coloured per year (amber for 6-campaign years, navy for 4) using the same per-category `dataPoint` selector that already works for the rating chart, `categoryAxis.axisType = 'Categorical'` for one label per year, and a visual-level filter `Year > 2012`. Page tabs shortened (Overview, Sales & Margin, Delivery & Returns, Inventory, Customers, Data Quality) so the navigator stops truncating, and Data Quality cards were cut to fit their text.

**Scatter → banded bars.** The scatter was still unreadable: its value axis ran to −100% when the lowest month is −41%, the 245px-tall chart squeezed most dots into one band near 0–20%, and the relationship isn't linear anyway. Grouping months by promo revenue share (CSV check: under 20% → 18.2% margin over 59 months; 20–60% → 7.1% over 42; 60% and above → −14.6% over 25) shows the real shape: margin turns negative once promotions pass 60% of a month's revenue. Built with a disconnected calculated table `'Promo Share Band'` (`DATATABLE` of band, order, min, max; registered in `model.tmdl`) and `Gross Margin % by Promo Band`, which filters `VALUES('Date'[Month Start])` to the months whose `[Promo Revenue Share %]` falls in the band, then computes margin over those months together. Bars coloured green / amber / red per band. A follow-up question showed the two kinds of % on the chart (band = promo share of revenue, bar = gross margin) were easy to mix up, so bands were relabelled "Promo <20% of revenue" / "Promo 20-60% of revenue" / "Promo ≥60% of revenue", and a `Months in Promo Band` tooltip shows how many months each bar is built on (axis labels are static table values, so the count can't live there).

## General lessons from this build

- **Confirm Power BI Desktop is closed before editing project files on disk.** Desktop holds its own in-memory copy and will overwrite external edits when it next saves.
- **The modern table visual does not stretch to fill its container.** Size tables to their content; let a *paired chart*, not the table, absorb any extra space.
- **`fromColumn` is the many/child side, `toColumn` is the one/parent side**, in every relationship, with no exceptions — reversing them fails to load with a duplicate-value error that doesn't obviously point at the relationship itself.
- **Two active relationships between the same pair of tables, through two different intermediate tables, is an ambiguous path.** Check for this whenever a new table relates to two tables that already relate to each other indirectly.
- **When a property isn't in Microsoft's official schema docs, treat it as best-effort**: implement it, but don't assume it rendered until confirmed from a screenshot, and don't be surprised if it's silently ignored rather than causing an error.
- **When a property *is* in the official schema (as with visual-level filters, confirmed via the published `filterConfiguration`/`semanticQuery` schema files), fetch and read the schema before writing JSON** — it is possible to get a genuinely undocumented-by-community but officially-specified feature right on the first try.
- **A `textbox` visual's `background`/`border` objects do not render or persist in Power BI Desktop** — confirmed by Desktop stripping them on save (Round 11). Table styling (`columnHeaders`/`values`/`grid`) and plain text colour *do* persist. For a coloured "card" look, use a `basicShape` rectangle behind the text instead.
- **If the report's colours match the base theme's first `dataColors`, the custom theme isn't loading.** Check that the `RegisteredResources` item's `path` in `report.json` names the theme file exactly, including `.json`.
- **Any rate whose outcome arrives after the order (returns, deliveries) is biased in the last few weeks of the data.** Measure the maximum lag from the raw data and exclude orders younger than it.
- **Never test a CSV-sourced text column with `ISBLANK`.** Empty cells arrive as `""`, which `ISBLANK` treats as non-blank. Use `LEN(col) > 0`.
- **Reconcile visuals against an independent calculation, not just against each other.** A chart that "only shows one line" or a table cell that's always empty is a symptom worth tracing, not a rendering quirk.
- **Anchor a "vs last year" measure on `MAX('Date'[Year])` in the current filter context, not `ALLSELECTED`.** This lets a YoY measure work correctly both at the report's All/All default (compares the latest year to the one before it) and when a single year is explicitly selected, without the `ALLSELECTED`-targets-the-wrong-column trap from Round 1/2.
